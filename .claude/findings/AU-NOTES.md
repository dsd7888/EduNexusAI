# AU-NOTES — Notes v2 generation + web math/diagrams + PDF export

**Audited:** 2026-08-16 · **HEAD:** `1367e5a7f54c1f40a9de0431d0ed6fb7bfaa0cd0` (branch `dev`, clean tree
except pre-existing untracked audit scaffolding from AU-CHAT)
**Scope:** `src/lib/notes/**`, `src/app/api/notes/**`, `src/app/(student)/student/notes/[subjectId]/page.tsx`
+ `_hooks/`, `src/components/notes/**`, `src/lib/pdf/builder.ts` (shared PDF engine, as invoked by
the notes export route). Flashcards (`notes/[subjectId]/flashcards`) are AU-FLASH's scope, not audited here.

**Method:** Dynamic throughout. `npm run dev` against the real `.env.local` (Supabase + Gemini),
driven with `src/lib/testing/httpHarness.ts` as an ephemeral student templated off the live
`teststudent@gmail.com` fixture (branch CSE, semester 3), plus direct Playwright browser sessions
authenticated as `teststudent@gmail.com` itself via the harness's magic-link-mint pattern. Real
subjects used: `SECE2250` (Computer Org, 8 modules, 0 pre-existing notes), `IDME3532` (Automobile
Eng, 4 modules, all 4 pre-generated by an earlier dev/test run), `SECE3260` (Cryptography, 6
modules, 1 pre-generated), `IDSH2020` (Maths III, 8 modules, 0 pre-existing notes — used for the
empty-state repro below). PDFs inspected with `pdftotext`/`pdfimages`/`pdftoppm` (poppler), not just
"200 OK". 3 real Gemini generations were made (₹1.3663 total, `feature=notes` correctly, not
`chat`). All audit-generated `study_notes` rows were deleted after inspection; `teststudent@gmail.com`
usage_analytics was left untouched (every read against it was a cache hit, which the code correctly
does not charge quota for). Harness scripts and captured screenshots/PDFs are under `_audit_notes/`
(untracked, not committed, same convention as AU-CHAT's `_audit_chat/`).

## Checklist results

**A. Happy path** — [RUNTIME] Module generation, subject assembly, cache-hit re-serve, and PDF
export (full-subject and single-module) all work correctly end to end *once module-scope rows
exist*. Block validation, id-slug derivation, hash-based freshness, and version numbering all
behaved exactly as documented in the code comments. See S1 below for the enormous caveat on
"once module-scope rows exist."

**B. Adversarial input** — **largely N/A by design**, and that is a legitimate finding, not a gap
in this audit: unlike chat, nothing in the Notes v2 pipeline takes free-text student input. Content
is generated solely from `subject_content` (faculty-owned syllabus text) on a schedule the student
does not control. The one adversarial surface actually reachable by a student — the in-page
**search box** — was fuzz-tested [RUNTIME]: a raw `<img src=x onerror=alert(1)>` payload and a
10k-char-class query both rendered inert (React's default escaping), zero console/page errors, zero
dialogs. Off-syllabus/injection/integrity-abuse/distress framings do not apply to this endpoint
class; the one place a student's own words reach an AI (the "Ask about this" → chat handoff) hands
off to `/student/chat/**`, which is AU-CHAT's surface and was audited there.

**C. Malformed / boundary input** — [RUNTIME] Garbage subject/module UUIDs, a SQL-injection-shaped
subject id, and a 10,000-character subject id all resolved to clean 404s, never a 500 or a stack
trace. Exporting before any subject-scope row exists returns a clean `404 no_notes` with plain-language
copy, not a crash.

**D. State / concurrency** — [RUNTIME] Tested by firing two genuinely parallel `GET
/api/notes/module/:id` requests at a module with zero existing notes rows (the shape of a student
double-tapping "Generate" or having two tabs open). See **S2-1** below — this is not clean.

**E. Authorization** — [RUNTIME], and this is the strongest part of the feature. Every axis holds:
a CSE student is refused (`403`) on a subject offered only to another branch; a module-id belonging
to an inaccessible subject is refused rather than silently generated; a plain student is refused
both regenerate routes (`403 Forbidden: Faculty only` / `...Faculty or Superadmin or Dean or Hod
only`); and — the sharper test — an **unassigned faculty** account (`role=faculty`, no
`faculty_assignments` row) is refused not just the regenerate routes but the plain read route too
(`403 Forbidden: subject is not assigned to this faculty`), proving the scope gate is real and not
just a role gate. `_moduleId` routing metadata never leaked into a client response in any of the
three response shapes checked (module GET, subject GET, PDF export path).

**F. Errors & logs** — Mixed. Most error paths are clean, plain-language, DESIGN.md-voiced (`"Generate
notes first"`, `"Nothing matched... Try a shorter word"`). One path leaks a raw Postgres constraint
name straight to the client — see **S2-1**.

**G. Cost / logging** — [RUNTIME] Verified against `ai_call_logs`: all 3 real generations this run
landed with `feature=notes` (never the v1 `chat` mislabelling CLAUDE.md warns about), `task=notes_gen_module`,
Flash-tier cost (₹0.39–₹0.51/call). Subject assembly and PDF export correctly make **zero** AI calls
(confirmed no new `ai_call_logs` rows from either) — the aggregate-cost bookkeeping in
`subject-assembler.ts` is not lying. But the concurrency bug (S2-1) means one logical student action
can silently double real spend — see below.

**H. UI/UX (DESIGN.md)** — [UI] The reading page itself is well-built and conforms closely: ink/ochre
palette, Plex Serif/Sans hierarchy, `mono-tag`-ish relatedTerms chips, hairline dividers, real empty
states in the platform voice. Every notes-page-specific control measured **≥44px** on mobile
(`Ask about this` 44×316, module filter chips 44×119–290, `Flashcard mode`/`Download` 44×178–192) —
this page does *not* reproduce AU-CHAT's touch-target bug. Two things do reproduce AU-CHAT's already-logged
cross-cutting findings and are not re-counted as new here: **dark mode is unreachable** (`colorScheme:
"dark"` context produces a byte-identical render to light — confirms the ledger's finding applies here
too), and the **desktop sidebar has no collapse control** (same shared `(student)/layout.tsx`). The
**hamburger menu button measures 36×36px**, under the 44px floor — also the same shared-shell element
AU-CHAT already flagged, not new. New to this feature: the **PDF export's color/type system is not
DESIGN.md's** — see **S3-1**.

## Findings

**[S1] [RUNTIME] The Notes v2 feature has no reachable path to ever generate its own content — it
is dead for every real subject except the ones a developer happened to seed by hand.**

- **What:** The student reading page (`(student)/student/notes/[subjectId]/page.tsx` via
  `useSubjectNotes.ts`) calls exactly one endpoint: `GET /api/notes/subject/:subjectId`. That route
  (`api/notes/subject/[subjectId]/route.ts`) — by explicit design, per its own file header — **never
  generates missing module notes**; `assembleSubjectNotes` (`subject-assembler.ts`) only reads
  *already-fresh* module-scope rows and returns `no_module_notes` if none exist. The only code path
  that ever calls `generateModuleNotes` (the function that actually talks to Gemini and writes a row)
  is `GET /api/notes/module/:moduleId` and the two `*/regenerate` routes. Grepping the entire student,
  faculty, and superadmin UI trees (`src/app/(student)/**`, `src/app/(faculty)/**`,
  `src/app/(superadmin)/**`, `src/components/**`) for any reference to `/api/notes/module` or a
  `regenerate` call returns **zero results**. There is no button, page, cron, or webhook anywhere in
  the product that invokes first-time module generation.
- **Evidence:** Of the 9 real subjects offered to the live `teststudent@gmail.com` fixture's branch
  (CSE), 7 had **zero** `study_notes` rows before this audit touched them (`IDSH2020`, `SECH3211`,
  `SECH3250`, `IDCH3051`, `SEME2321`, `IDME2010`, `SECE2250`); only 2 had any, both bearing
  timestamps (`2026-07-31`, `2026-08-07`) and row counts consistent with a developer's `_cp_n*_verify`
  harness run, not organic product use. Live-browser repro against `IDSH2020` (real
  `teststudent@gmail.com` session, zero rows): page loads, shows the exact error `"No module notes
  are available for this subject yet (0 of 8 modules covered)"` with a **"Generate notes" button**.
  Clicking that button (`onRetry={reload}` → re-fetches the *same* subject GET) leaves
  `study_notes` at **0 rows**, confirmed by direct DB query immediately after the click, and the page
  settles back into the byte-identical error state — an infinite loop with a button that implies
  action but performs none. Screenshots: `_audit_notes/empty-path-1-initial.png`,
  `empty-path-2-after-retry.png` (mid-fetch skeleton), `empty-path-3-settled-after-retry.png` (back
  to the identical error).
- **Where:** `src/app/(student)/student/notes/[subjectId]/page.tsx:452` (`ErrorState`'s "Generate
  notes" button), `src/app/(student)/student/notes/_hooks/useSubjectNotes.ts:83` (the only endpoint
  ever called), `src/app/api/notes/subject/[subjectId]/route.ts` (never calls `generateModuleNotes`),
  `src/lib/notes/subject-assembler.ts` (assembly-only, by design — correct in isolation, but nothing
  upstream of it ever seeds what it assembles).
- **Recommendation:** Either (a) give the student-facing "Generate notes" button a real action — call
  `generateModuleNotes` for each uncovered module (sequentially, mirroring the subject-regenerate
  route's own concurrency-safety comment) when the subject route reports `no_module_notes`, gated by
  the existing `notes_view` rate limit so this doesn't become a cost hole; or (b) if notes are meant
  to be faculty-provisioned ahead of time (matching the "faculty tier only" language throughout
  `access.ts`/`generator.ts`), ship the faculty-facing regenerate UI that currently does not exist
  anywhere, and treat every currently-offered subject as needing a one-time backfill before this
  ships to students. Right now neither exists, so the feature has no cold-start path at all.

**[S2-1] [RUNTIME] Two concurrent requests for the same not-yet-generated module double real AI
spend and hand the loser a raw Postgres error message.**

- **What:** `generateModuleNotes` (`generator.ts`) computes `version = maxVersion + 1` from a read
  taken at the *start* of the request, with no locking. Two concurrent callers (double-click, two
  tabs, a slow network retry racing the original) both read `maxVersion = 0`, both make a real,
  separately-billed Gemini call, and both attempt to insert `version = 1`. The DB's partial unique
  index (`study_notes_module_version_key`, `20260730000000_notes_v2.sql`) correctly prevents silent
  duplication — but the *loser's* insert throws, and `generator.ts`'s catch-all surfaces
  `insertError.message` verbatim as the API response's `message` field.
- **Evidence:** [RUNTIME] repro against `SECE3260` module 3 (no prior notes row), two genuinely
  parallel `fetch` calls to `GET /api/notes/module/:id`: **A → 200** (fresh, stored), **B → 500**
  with body `{"error":"storage_failed","message":"duplicate key value violates unique constraint
  \"study_notes_module_version_key\""}`. `ai_call_logs` confirms **both** calls billed
  (`task=notes_gen_module, status=success, cost=0.5125` and `cost=0.3863` — the DB-constraint failure
  happens strictly after the paid Gemini call returns, so nothing about the failure avoids the
  spend). Full transcript in `_audit_notes/run1.log`, §6.
- **Where:** `src/lib/notes/generator.ts:442-479` (unlocked read-then-insert of `version`), surfaced
  via `src/app/api/notes/module/[moduleId]/route.ts:98-115` and the identical pattern in
  `subject-assembler.ts`'s own insert.
- **Recommendation:** Two independent fixes, both cheap: (1) don't leak `insertError.message` to the
  client — log it server-side, return the same plain-language "couldn't build your notes, try again"
  copy the other error branches already use; (2) either take a request-scoped lock/mutex keyed on
  `(subjectId, moduleId)` before generating, or catch the unique-constraint violation specifically and
  fall through to re-reading the now-committed sibling row instead of erroring, so the loser's *paid*
  generation isn't simply thrown away.

**[S3-1] [EXPORT] The PDF export's color and type system is generic Tailwind-blue/Helvetica, not
DESIGN.md's ink/ochre/Plex system.**

- **What:** `COLORS` in `src/lib/pdf/builder.ts:20-31` hard-codes `primary: #2563EB` (Tailwind
  `blue-600`), `dark: #1E40AF`, `border: #E2E8F0` — none of which are DESIGN.md tokens (`ink #14293D`,
  `ochre #C08A2E`, `paper #F5F6F4`). Fonts are `StandardFonts.Helvetica*`
  (`builder.ts:1336-1339`), not IBM Plex Serif/Sans. Every notes PDF header, module-section rule, and
  card-title color is this off-brand blue.
- **Evidence:** [EXPORT] Visual inspection of `_audit_notes/out-full.pdf` (rendered to PNG via
  `pdftoppm`, see `_audit_notes/p1-1.png`) — a bright royal-blue header band and body copy in a
  generic sans, both clearly distinguishable from the reading page's own on-brand rendering
  (`_audit_notes/reading-desktop-viewport-top.png`) taken minutes apart from the same content.
- **Where:** `src/lib/pdf/builder.ts:20-31` (`COLORS`), `:1336-1339` (font embedding). **Cross-cutting**,
  not notes-specific: per CLAUDE.md, `PDFBuilder` "backs every `/api/.../export` route (chat, notes,
  quiz, placement)" — this is very likely the same off-brand rendering in every PDF the platform
  produces, not something to fix four times.
- **Recommendation:** Convert DESIGN.md's ink/ochre/paper hex values to the `PDFBuilder`'s `rgb()`
  calls and swap the embedded fonts for IBM Plex (pdf-lib supports custom font embedding via
  `fontkit`, which the general `next/font` self-hosting pattern already implies is available in this
  repo). One shared fix, not a per-export one.

**[S3-2] [RUNTIME] Generation quality: a `formula.symbols[].symbol` field is sometimes a full phrase
instead of a short symbol, defeating the point of the column.**

- **What:** The real "Steering Ratio" formula block generated during this audit has symbol rows
  `"Steering Wheel Angle"` / `"Road Wheel Angle"` in the **Symbol** column (paired with an identical
  string repeated as the meaning's subject) instead of a short notation like `θ_sw` / `θ_rw`. The
  prompt's own few-shot examples (`prompts.ts`, `FORMULA — GOOD`) model this correctly (`V`, `I`,
  `R`), and the validator's 20-char `symbol` length cap doesn't catch this because "Steering Wheel
  Angle" happens to fit in exactly 20 characters — the bound polices length, not whether the field is
  actually a symbol.
- **Evidence:** [RUNTIME] `_audit_notes/out-full.pdf` p.4 / `_audit_notes/page-4.png`; same data
  visible in the raw JSON response logged in `_audit_notes/run1.log`.
- **Where:** `src/lib/notes/prompts.ts` (`FORMULA_SCHEMA`, `BLOCK_EXAMPLES`).
- **Recommendation:** Low-priority prompt tightening only — e.g. an explicit bad-example pair showing
  a descriptive phrase used as a symbol, mirroring the `whyItMatters LENGTH — BAD` pattern already in
  the file. Not urgent; one instance in one generation, not a validator gap worth a hard reject.

**[S3-3] [STATIC] Non-Latin/unusual-unicode characters in notes text (outside recognized `$…$` math
spans) are silently dropped from PDF exports, not substituted or flagged.**

- **What:** `src/lib/pdf/builder.ts:224-228`'s plain-text sanitizer has an explicit table converting
  common math/Greek symbols to ASCII (°, ×, π, Ω, μ, θ, …) but ends with a catch-all
  `.replace(/[^\x00-\x7F]/g, "")` — any remaining non-ASCII character (an em dash, a smart quote, a
  right-arrow "→" the model might use in prose, or literal Hindi/regional-script text) is deleted
  outright rather than transliterated or preserved.
- **Evidence:** [STATIC] — not reproduced in a real generation this run (none of the 3 real
  generations happened to contain such a character; the export text extraction in
  `_audit_notes/out-full.txt` shows zero non-ASCII survivors, consistent with either "none were
  present" or "they were silently stripped" — this audit could not distinguish the two without a
  crafted input, which the pipeline offers no way to inject). Flagged as lower-confidence for that
  reason.
- **Where:** `src/lib/pdf/builder.ts:224-228`.
- **Recommendation:** At minimum, log when this branch actually strips a character (currently
  silent), so a future occurrence is detectable in server logs rather than only as a student noticing
  a word is missing from their downloaded PDF.
