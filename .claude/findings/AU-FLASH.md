## Findings

**[S2-1] [RUNTIME] Two `go()` calls (Next/Previous clicks, or Arrow-key presses) that land in the same
React render batch collapse into a single card advance, silently dropping the second navigation input.**

- **What:** `go(delta)` in `page.tsx` computes `next = safeIndex + delta` by reading `safeIndex` from
  the closure captured at the last commit, then calls `setIndex(next)`. If two calls to `go(1)` (or any
  two `go()` calls) execute before React flushes a re-render — which happens whenever two DOM click/
  keydown events are dispatched within the same task/batch — **both** read the *same* pre-click
  `safeIndex` and compute the *same* target index, so the second call is a no-op (`next === safeIndex`
  is true on the second read... except it isn't recomputed at all: both writes just set the identical
  value, so React coalesces them into one visible transition either way). Net effect: what should be a
  2-card (or 3-card) advance renders as a 1-card advance, with no error, no visual indication, and no
  way for the student to tell it happened.
- **Evidence:** [RUNTIME], three independent reproductions, isolated from the `revealed`-toggle logic to
  rule out interference from that state:
  1. Two synchronous `.click()` calls dispatched on the "Next card" button in the same JS task (a real
     `click` event pair, not a synthetic bypass) → counter moved **Card 1 → Card 2**, not Card 3.
  2. Three synchronous `.click()` calls the same way → counter *still* only moved to **Card 2**, not
     Card 4 — every click after the first in the batch is lost, not just the second.
  3. Two synchronous `ArrowRight` keydowns dispatched from an already-revealed card (both correctly
     take the "advance" branch of the handler, ruling out the reveal/advance toggle as the cause) →
     counter moved **Card 1 → Card 2**, not Card 3.
  Screenshot of the settled (under-advanced) state: `14-double-advance-repro.png`. Full transcripts:
  `_audit_flash/ui3.mts` (the isolated repro) — console output:
  ```
  before: Card 1 of 23
  after two synchronous next-clicks (expect Card 3 if both counted): Card 2 of 23
  after three synchronous next-clicks (expect Card 4 if all counted): Card 2 of 23
  after two synchronous ArrowRight (expect Card 3 if both counted): Card 2 of 23
  ```
- **Where:** `src/app/(student)/student/notes/[subjectId]/flashcards/page.tsx:115-126` (`go`), invoked
  from the Previous/Next `onClick` handlers (`:281`, `:297`) and the keyboard handler's advance branch
  (`:147`). The pointer/swipe handler (`onPointerUp:159-170`) calls the same `go`, so a rapid double-swipe
  is very likely the same failure mode, though this run reproduced it via buttons and keys specifically
  (not swipe) to keep the repro clean and attributable.
- **Realistic trigger, stated honestly:** the clean repro here used two `.click()`/`dispatchEvent` calls
  issued back-to-back in one JS task, which reliably falls inside one React batch — that is a stronger
  condition than a leisurely human double-click (two clicks 150–300ms apart typically each get their own
  render). The condition is genuinely reachable by a real student, though: (a) **keyboard key-repeat** —
  holding ArrowRight down (a very natural way to skip through a deck fast) fires repeated keydowns fast
  enough, especially if a render is briefly slow (KaTeX/formula rendering on a card), to land two in one
  batch; (b) a **fast double-tap on a lower-end phone** under real "night before the exam, one-handed,
  tired" use (the page's own stated target scenario) is not implausible at the same frame-timing margins.
  Framed precisely: this is a real defect in the core loop's state-update logic, demonstrated with a
  deterministic repro; how *often* real users hit the exact timing window this run couldn't measure.
- **Recommendation:** Use the functional updater form for `setIndex` (`setIndex(i => clamp(i + delta, 0,
  cards.length - 1))`) instead of computing `next` from the closed-over `safeIndex`, so each queued update
  applies against the *result* of the previous one rather than against a shared stale read. `setRevealed(false)`
  can stay as-is (it doesn't depend on the deck position). This is the direct counterpart to the bug the
  file's own header comment already fixed in the *other* direction (an updater that had a side effect) —
  the fix here is the opposite: this closure-read *needs* to become an updater, not stay a plain value read.

  double-swipe (both directions call `go` identically), but this run only reproduced it via button clicks
  and key presses, which isolate the root cause more cleanly than simulating two overlapping pointer
  drag sequences would. Flagging as very likely, not independently confirmed via swipe.

  region, and card content changes (reveal, advance) are not announced. Not independently verified with

  same `notes_view`-gated route AU-NOTES already exercised for rate-limit boundary/concurrency); not
  re-tested here as it would be a pure duplicate of that work.
